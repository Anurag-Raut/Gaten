## Static findings and constraints

The screenshot path intentionally makes one full-screen ARGB_8888 software copy in `GatenAccessibilityService.kt:499-520`, then shares it with the overlay and OCR. `BitmapRepository.clear()` drops its reference, but bitmap lifetime is also governed by the `ImageView`, Compose tree, OCR jobs, and native tasks. No safe source-only recycling change was established.

`ScreenLineReader` caches in-flight and completed per-line reads (`ocr/ScreenLineReader.kt:67-75, 121-151`). Prefetch reprioritization cancels only its ordering coroutine; an existing deferred remains joinable. Ordinary prefetch therefore does not reread a line. Meiki full-screen tiling and byte-array/model reload work, and manga-ocr decoder full-prefix repetition, remain static cost candidates; no device timing exists. The 90-second idle release, native ML Kit Task pinning, session locks, and current ONNX allocator defaults remain required.

Reviewed without a clear source-only optimization: Home `onResume` checks and preference reads, streaming model downloads, Anki/provider I/O and status handling, trigger receiver/tile/activity entrypoints, ABI splits, and release shrinking. These remain measure-first areas; no behavior change is proposed from inspection alone.

The empty-placeholder manga acceptance limit is 16 characters in the current policy. Circle crop acceptance deliberately bypasses that short-text limit. This audit does not weaken either filter. No BGR/letterbox failing-screen evidence exists.

Dictionary asset inspection found `idx_terms_term` and `idx_names_term`. Main lookup uses the term index, joins entries by primary key, and sorts via a temporary ordering step; observed asset statistics were average 1.07 and maximum 51 rows per term. Name lookup averaged 1.22 and max 34 rows, so no extra ordering/`LIMIT` was added to `NAME_LOOKUP_SQL`. Its column-order defect is fixed (see table).

Measured artifact facts: generated SQLite is 94,760,960 bytes; packaged SQLite is 42,721,671 bytes; packaged meiki is 37,875,701 bytes (raw meiki 41,593,485 bytes); arm64 debug APK is 166,685,886 bytes. There is no release or baseline size comparison, so these are not claimed reductions.

Validation recorded for the first tranche: `:app:testDebugUnitTest` ran 307 JVM tests with zero failures, errors, or skips, and `:app:assembleDebug` succeeded (re-confirmed after the scan/name-SQL/cancellation fixes). These checks do not prove Android Bitmap/Compose runtime behavior, native lifetime safety, OCR accuracy, PSS, battery, or latency.

## Measured results

Bounded paired pass on Moto g35 5G (Android 15), baseline vs first-tranche optimized APK, identical manga-ocr model files, stable Japanese Wikipedia scene (content hash `b198f2f8…`), `CLK_TCK=100` verified. Full report: `.gradle/device-audit/REPORT.md`.

| Metric | Baseline | Optimized |
|---|---|---|
| Idle-overlay process CPU (post-prefetch, guarded windows) | 21.35–25.55% of one core | ~0.05% |
| True-idle (>90 s, models released) PSS / native heap | 100–152 MB / 18.5–26.5 MB | 83–95 MB / 0.64–12.8 MB |
| Overlay-open PSS / native (during capture+inference) | 512–515 MB / 176–229 MB | ~500 MB / ~217 MB |
| Scan ready / meiki / warm manga read | 1312–2588 ms / 7891–9109 ms / 528–1569 ms | 2856 ms / 7261 ms / 524–1569 ms |
| Circle correctness | 孤立した言語 → "language isolate" etc. | identical behavior |

Supported conclusions: the idle `EdgeOutline` animation was a real ~21–26%-of-a-core cost and its removal is the only strongly evidenced win; true-idle native heap is directionally lower but n=1–2 with overlap, so the bitmap-recycling win is provisional. Timings are indistinguishable (run-to-run variance exceeds any difference). No battery claim is made from short powered samples; `gfxinfo` reported 0 frames in both idle states. The downloader cancellation fix was not exercised (no cancel during install). Device settings changed: Gaten accessibility service enabled (appended, none removed); optimized APK left installed; identical model files preserved across `install -r`.
